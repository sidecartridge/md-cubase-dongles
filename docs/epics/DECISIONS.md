# Decisions

Lightweight log of cross-cutting decisions referenced by the epics/stories.
Statuses: **accepted** / **proposed** / **open**. Link decisions from stories as
`D-NN`.

| ID | Decision | Status |
| --- | --- | --- |
| D-01 | v1 scope is the **Cubase 3 red dongle only** (Intel 5C060 / EP600). It is the best-sourced target: full JEDEC fuse map + de-fused equations + two m68k golden models (CUBASE.S, CUBSCORE.S). The Cubase 2 "black dongle" (routine A) and the Cubase Audio Falcon dual dongle (a different Xilinx XC9536XL chip) are out of scope; the architecture stays extensible to them. Diego, 2026-08-19. | accepted |
| D-02 | **Commit derived artifacts + provenance hashes only.** This repo publishes to a public microfirmware store, so the raw reverse-engineered files (JEDEC fuse map `SRD_OK`, de-fused equations `srd_ok.jed.txt`, Medway Boys crack `CUBASE.S`) are NOT committed. Committed: the generated `rp/src/include/cubase_lut.h`, the golden vectors, and `tools/reference/PROVENANCE.md` (SHA-256 of each source + the full-transition signature). `tools/generate_lut.py` reads the raw sources via `--source-dir`; `.gitignore` guards their filenames. Diego, 2026-08-19. | accepted |
| D-03 | **Modal design, committed via the setup menu (revised 2026-08-20 with Diego).** The setup menu needs ROM4 (`romemul`, cartridge code) + ROM3 (`commemul`, command channel). The Cubase dongle needs **none** of that infrastructure. So the `[F]irmware` menu command is the **mode commit** (like `md-devops`'s runner / `CMD_START`): on it the RP tears down the setup PIO and stands up a dedicated ROM3 dongle engine, while the m68k side boots straight to GEM. (The Core1 build frees only `commemul`, leaving `romemul`/ROM4 up; the PIO+DMA build (D-09) frees `romemul` too — ROM4 goes open-bus, safe because Cubase never reads the cartridge after boot.) The dongle engine keeps running so Cubase can query it. There is no "return to the menu" from a commit (reset the MultiDevice for setup) — that is the framework, confirmed on hardware. EPIC-04 verified the drive works; EPIC-06 wires the commit + teardown. | accepted |
| D-04 | **Runtime engine: Core1 busy-poll is the v1 baseline; pure PIO+DMA is the target end-state (Iteration 3).** The dongle's per-access bus handling is the **ROM4 romemul dance at smaller scale** (D-08): read A8, drive D8. Core1 busy-poll (PIO does the bus dance + captures A8; Core1 does the LUT step and stages the next output) is correctness-first and easy to verify against the golden model. Pure PIO+DMA (state fed back through DMA, no CPU) removes the timing race (C-03) but is intricate; it is Diego's preferred end-state. **DONE + hardware-verified as EPIC-07** (see D-09); the Core1 build is kept in the repo as the reference/fallback. | accepted |
| D-08 | **The ROM3 dongle handling is the romemul ROM4 dance, minimized (confirmed with Diego 2026-08-20).** Per ROM3 access: (1) detect the access (wait on `/ROM3` = GP26); (2) assert `!READ` (GP27), settle, sample **A8** — the input — which is **GP14** during the address phase (`READ_ADDR_GPIO_BASE 6` + 8); (3) flip the shared bus to output and assert `!WRITE` (GP28) to drive **D8** — the output — which is the **same pin GP14** during the data phase (`WRITE_DATA_GPIO_BASE == READ_ADDR_GPIO_BASE`); we drive the whole word `0xFEFF`/`0xFFFF` (D6). The state advances on the **rising edge of `/ROM3`** (access end), so the D8 driven during an access is the *previous* state's output (pre-staged) — reset output is pre-staged before the first access. This is exactly romemul but indexing the 6150-state LUT by A8 instead of RAM by the full address. | accepted |
| D-05 | **pin15 power-on ambiguity is behaviorally moot.** The HDL/equations do not reset pin15. Verified (2026-08-19) that from pin15=0 (state 0x0000) and pin15=1 (state 0x0100) the D8 output stream is identical for any A8 input (1 M random steps; converges). The runtime uses the pin15=0 reset (matching CUBASE.S / MiSTer); the LUT is built over the union of both universes (6150 states) so the exact silicon power-on is covered either way. | accepted |
| D-06 | **Data word driven on a dongle read = `0xFEFF` (D8=0) / `0xFFFF` (D8=1)**, i.e. all non-D8 lines high, mirroring the MiSTer core's `{7'h7f, cubase3_d8}`. CONFIRMED on hardware 2026-08-20: **Cubase 3.10 and Cubase Score 2.0** both accept the dongle and run, on both the Core1 (EPIC-05) and PIO+DMA (EPIC-07) engines — two independent applications masking the read to D8 as expected. | accepted |
| D-07 | **The dongle lives on ROM3** ($FB0000), as the real 5C060 does. CONFIRMED on hardware 2026-08-20: EPIC-04 gate #1 passed (ST reads FEFF from $FB0000), so the MultiDevice can drive ROM3 data. No ROM4 pivot needed. | accepted |
| D-09 | **As-built zero-CPU PIO+DMA engine (EPIC-07), verified on hardware 2026-08-20.** State lives in PIO scratch reg Y; the PIO builds the LUT address `base \| (state<<3)\|(a8<<2)` and two chained DMAs do the lookup + next-state feedback (romemul's address→data trick), no CPU. Three consequences that refine earlier decisions: (a) the 23-instr program needs all of pio0, so the commit frees **both** commemul and romemul (revises D-03; ROM4 open-bus, safe). (b) A single self-contained access replaces D-08's pre-staging: the entry stores `output_word(CURRENT state)` — the 5C060's registered output — so D8 during access N reflects S_N and A8_N picks S_{N+1}. Per-state D8 is derived from the committed 16-bit LUT (each entry carries its next state's D8). (c) The 48 KB `{output_word, next_state}` table is built into the freed, 64 KB-aligned ROM_IN_RAM at commit (revises C-05). Freeing romemul must wait for the m68k to read CMD_START + run userfw, so `cmdEnterGem` inserts a fixed `GEM_BOOT_SETTLE_MS` (1500 ms) delay — a timing heuristic, the knob if a slower GEM boot ever races the free. | accepted |

## Constraints

| ID | Constraint |
| --- | --- |
| C-01 | **PIO instruction budget forces the modal design.** pio0 holds `romemul` (16 instr) + `commemul` (10) = 26 of 32 words, leaving only 6. A correct cubase ROM3 program is ~13 instructions and cannot coexist; so dongle mode loads *neither* `commemul` nor (needed) `romemul`, and owns pio0 alone. pio1 is nominally free but the pico_w CYW43 driver typically claims a pio1 SM. |
| C-02 | **No logic analyzer available** (Diego has MultiDevice + ST only). Verification leans on exhaustive host-side golden-model cross-checks plus functional "does Cubase accept it and boot" testing. Fine bus-timing (D-06, burst behavior) can only be confirmed functionally, not captured. |
| C-03 | **The cartridge bus has no DTACK / no flow control.** The RP cannot insert wait states, so it cannot stall a read until data is ready. The per-access response must always beat the ST inter-access gap; a late handler drives stale data → wrong D8. **Resolved by EPIC-07's PIO+DMA engine (D-09):** each access is served entirely within the access by PIO+DMA, so there is no between-access compute to lose the race. |
| C-04 | **The LUT must be SRAM-resident.** 24 KB exceeds the 16 KB XIP flash cache, so a flash-resident `const` table would cause nondeterministic fetch stalls in the Core1 handler. The generated array is non-const (lands in `.data`/SRAM) and the handler is `__not_in_flash_func`. |
| C-05 | **RP2040 has 264 KB SRAM** (MultiDevice reserves ~192 KB general RAM + a 64 KB ROM_IN_RAM region). The Core1 build keeps its 24 KB LUT in `.data`/SRAM. The PIO+DMA build (D-09) reuses the freed, 64 KB-aligned ROM_IN_RAM (0x20030000) in dongle mode to host the 48 KB `{output_word, next_state}` table, below the display framebuffer. |
